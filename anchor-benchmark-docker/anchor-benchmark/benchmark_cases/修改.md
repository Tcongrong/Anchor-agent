# Benchmark Case 结构修改方案（Structural Fix Plan）

## 0. 与 `审查.md` 的关系 / 使用流程

本文件是 [`审查.md`](审查.md) 的**配套修改手册**，二者配合，流程固定为**先审查、再修改**：

1. **先审查**：用 `审查.md`（§0–§15）逐项审查某个 `benchmark_cases/<case_id>/`，产出
   一份 `<case_id> 结构审查报告`（格式见 `审查.md` §9，含 A/A2/A3/A4/A5/A6/A7/B…I/H 各卡）。
   审查阶段**只发现并分类问题**，不动手改。
2. **再修改**：拿审查报告里被标 **BLOCKING / WARN / 风险** 的条目，到本文件找对应
   修改项（`M1…M12`，每项注明由 `审查.md` 哪一节触发），按优先级 `P0 → P1 → P2` 执行。

分工：
- `审查.md` 回答"**哪里有问题、多严重**"（检测 + 判级 + 报告）；
- `修改.md`（本文件）回答"**具体改什么、改在哪个文件、改完怎样算通过**"（动作 + done 条件）。

**纪律（继承 `审查.md` §0.1）**：
- 修改非标杆 case 时，**以 `case001_browser_fingerprint` 的目录树与文件职责为准重组**，
  不在旧扁平布局上打补丁（见 M1）。
- 任一修改项完成后，**必须重跑 `审查.md` 对应节**确认转 PASS；涉及 oracle 坐标的，
  必须重跑 `gen_oracle_spans.mjs` + `verify.mjs` 并做 §4.1.3–4.1.5 语义复核（见
  `审查.md` §0.1 双轨验证）。
- **轨 A（hash 自洽）≠ 修改完成**；必须轨 B（span 语义正确）同时满足。

## 0.1 修改重中之重（贯穿所有 M 项，零容错）

1. **框架严格对标 `case001_browser_fingerprint`，但严禁直接复制粘贴内容**：目录树、
   `agent_visible/agent_hidden` 分区、`task.json` 提交 schema、oracle 的
   `answer_function`/`source_function` 双轨命名、脚本路径约定、
   `build → 同步 captures → gen_oracle_spans` 闭环，**一律以
   `benchmark_cases/case001_browser_fingerprint/` 的实现为唯一标杆**（见
   `审查.md` §14）。但**必须按本 case 自己的 src/题面/答案重写内容**——照抄 case001
   的字段值、selector、函数名、`captured_span` 坐标、`data-scan` 等会直接产生**错误
   答案**与**泄漏**，属严重事故。一句话：**"参考结构，不搬运内容。"**

2. **任何修改都必须先评估对【答案(oracle)】与【captures】的影响；一旦受影响，必须
   同步更新，不得遗留**：
   - **判断是否触及 bundle**：改动 `src/**`、`build.mjs`、混淆配置/`seed`、依赖版本、
     目录结构、文件命名等，**几乎一定会改变 bundle 字节级内容**，从而使
     `agent_visible/captures/` 的 bundle 与 `oracle.hidden.json` 的全部
     `captured_span` / `hash` / `answer_function` **整体或局部失效**。
   - **受影响时的强制流程**（缺一不可）：
     `重新 npm run build` → **同步 `dist/` bundle 到 `agent_visible/captures/`** →
     **重跑 `gen_oracle_spans.mjs` 重算全部坐标/hash/answer_function** →
     按 `审查.md` §4.1.3–4.1.5 做**轨 B 语义复核**（完整函数体、多同名不混、anchor
     字节数合理）→ 跑 `verify.mjs` → 必要时同步 `build_meta` 的 bundle 体积/行数声明。
   - **严禁**只改 `src/` 而不更新 captures/oracle——这正是 `审查.md` §10.6（hash 自洽
     假通过）/§10.7（模板克隆未同步）的事故模式，会让 oracle **静默失效**。
   - **每个 M 项的 done 条件都隐含追加一问**："本次改动是否触及 bundle？若是，
     captures 与 oracle 是否已同步重生成，并通过 §4.1.3–4.1.5 语义复核与
     `审查.md` §0 的'审查重中之重'三问复检？"未答即视为该 M 项**未完成**。

3. **M1–M12 不是封闭清单；审查发现的、本手册未覆盖的问题同样必须处理**：若
   `审查.md` 跑出的报告里出现**任何**无法对应到 M1–M12 的 BLOCKING / WARN / 风险
   条目（例如某个 case 特有的结构缺陷、新出现的泄漏渠道、未预见的 verify↔oracle
   冲突、论文/规范更新带来的新约束），**不得**因"修改书里没写"而跳过、降级或留待
   以后。处理标准与既有 M 项**完全一致**：
   - **详细分析**：写清问题表象、根因、触发的 `审查.md` 章节、严重级别，以及对
     【答案(oracle)】与【captures】的影响面；
   - **就地补项并修复**：按本手册体例**追加一个新的修改项**（顺延编号 `M13`、
     `M14`…），写明 触发审查节 / 改动内容 / 落地位置 / done 条件，并据此修改到位；
   - 新项同样受本节第 1–2 条约束（对标 `case001_browser_fingerprint` 但不照抄内容；
     评估并在受影响时同步重生成 captures/oracle 并做语义复核）。
   - 换言之：**审查能查出的每一个问题，都必须在 `修改.md` 里有归宿**——要么命中
     既有 M 项，要么新增 M 项；不允许"审查报告里有、修改书里无人认领"的悬空缺陷。

## 2. P0 修改项（阻断级，先于一切）

### M1 迁移到 canonical 目录分区（触发：审查 §12.5 / §14 / §10.16）

**问题**：`task.json` / `oracle.hidden.json` / `src/` 仍平铺在 `<case_id>/` 根下（旧
扁平布局），评测打包极易误发私有文件，agent 可见边界形同虚设。标杆
`case001_browser_fingerprint` 已物理隔离为 `agent_visible/` + `agent_hidden/`。

**改动内容**（即 `审查.md` §14.3 迁移清单，落地为可执行步骤）：
1. 创建 `agent_visible/`、`agent_hidden/`；
2. 移动 `task.json`、`captures/` → `agent_visible/`；
3. 移动 `oracle.hidden.json`、`build_meta.hidden.json`、`src/`、`scripts/`、`dist/`、
   `package.json` → `agent_hidden/`；
4. 更新所有脚本中的 `caseRoot`/`hiddenRoot`/`visibleRoot`（`build.mjs` 写
   `../agent_visible/captures/`，读写 oracle 以 `agent_hidden/` 为根）；
5. 更新 oracle/build_meta 内路径引用（`captured_span.file` 用相对 `agent_visible/`
   的 `captures/...`；`target_reference.task_file` 用 `agent_visible/task.json`）；
6. case 根加 `README.md` 说明分区；
7. 跑 `cd agent_hidden && npm run build && npm run verify`；
8. 确认 agent 打包目录**仅** `agent_visible/`。

**落地位置**：整个 `<case_id>/` 目录树。
**done 条件**：审查 §14.4 判 PASS；报告 A7 全 PASS；`cd agent_hidden && npm run verify`
通过。

### M2 anchor 唯一性 + 双轨命名补全（触发：审查 §12.1 / §12.2 / §10.11 / §10.13）

**问题**：读完 case 仍无法确定"anchor 是哪个函数"，或 oracle 只用源侧名
（`primary_anchor.function: assembleBrowserFingerprint`）当标准答案——而 agent 只能看
`captures/` 混淆 bundle，根本不知道源侧名。benchmark 在逻辑上不成立。

**改动内容**：
1. 在 `oracle.hidden.json` 写全 `primary_anchor`：`answer_function`（bundle 切片行首
   名，=agent 应提交的 `function_name`）、`source_function`（`src/` 私有映射）、
   `source_file`、`captured_span`（grader 主判据）、`answer_basis`（"以 captures span
   + answer_function 为准"）、`why`/`anchor_definition`、`score:1`；
2. `role_oracle` 中 `role:"Anchor"` **有且仅有 1 条**，其 `answer_function`+`captured_span`
   与 `primary_anchor` 一致；
3. **每条** `role_oracle[]` 补 `answer_function`（bundle 切片提取）+ `source_function`
   （源侧名）；多同名源函数（如 8 个 `r`）须 `source_function` 相同而 `answer_function`
   两两不同（`r$1`/`r$3`/`r$d`…）；
4. `build_meta.primary_anchor` 镜像 `answer_function`+`source_function`+span；
5. 删除遗留字段 `function`/`bundle_function`（避免 grader 误读源侧名为标准答案）；
6. `acceptable_hit_conditions`/`scoring_policy` 写明"以 span+answer_function 命中，
   `source_function` 不参与默认评分"。

**落地位置**：`agent_hidden/oracle.hidden.json`、`agent_hidden/build_meta.hidden.json`。
**done 条件**：审查 §12.1 表全满足；报告 **A4 Anchor 身份卡**可在 10 秒内答出标准答案名
+ 偏移 + 唯一性；A3 多同名映射表无错误合并。

### M3 修复 `gen_oracle_spans` 解析/合并 bug + span 语义错误（触发：审查 §4.1.3–4.1.5 / §10.1–10.5 / §11）

**问题**：span 仅含签名行（默认参数 `{}` 陷阱）、8 个 `r` 合并到同一 span、过宽别名
规则误匹配、仅用字符串字面量特征导致 unresolved——这些都能让 hash 44/44 自洽却
**切片是错的那个函数**（轨 A 通过、轨 B 失败）。

**改动内容**（对应 `审查.md` §11.1 必查表逐项修）：
1. 提取函数体前先**闭合参数列表 `(...)`** 再找第一个 `{`；用括号平衡取到结束 `}`
   （字符串/模板串内括号不计深度）；校验切片含 `return`/核心逻辑、以 `}` 结尾、
   `anchor` 字节数 >100；
2. **禁止"唯一同名即命中"短路**（删 `if (named.length===1) return named[0]`）；为每个
   `sourceKey` 做评分匹配（hex/结构/体积比 + 显式 `BUNDLE_HINTS`）；维护 `usedStarts`
   防抢占；
3. 泛化别名（如 `$1` 后缀）必须与 per-`sourceKey` 的 `BUNDLE_HINTS` 配合；有 hint 时
   只接受 hint 列表内的 bundle 名；
4. 特征集补 `0x` hex、字符码数组、`Math.imul`/`>>>` 结构、数组 key `\['xx'\]`，名称
   匹配优先于字面量分数、体积比 tie-break；
5. 生成后自检：写入 `duplicate_span_groups`（应为 0）、`anchor_bytes`、
   每条 `answer_function`；
6. 性能：1MB+ bundle 用括号扫描 + 字符串掩码，勿全量 AST。

**落地位置**：`agent_hidden/scripts/gen_oracle_spans.mjs`。
**done 条件**：跑脚本后审查 §4.1.3–4.1.5 全 PASS；报告 A2 无 span 语义错误、A3 各
offset 唯一；E2 工具链记录 exit 0 且独立复核通过。

### M4 task.json 提交 schema 与 oracle 对齐、example 不泄漏（触发：审查 §12.4 / §5.7）

**问题**：题面未规定 agent 输出 JSON 结构，或 example 泄漏真实 anchor，或要求 agent
填 `answer_function`/`captured_span` 等 oracle 私有字段。

**改动内容**：
1. `task.json: answer_format` 含 `response_type:"json"` + 完整 `response_schema`
   （`function_name` + `file` + `slice.{start_line,end_line,start_offset,end_offset,code}`）；
   `function_name` 描述强调"as it appears in captures"（非源侧名）；`slice.code` 要求
   **完整函数**（禁签名残片）；
2. `example` 用**占位名/假坐标**，文件路径可为 captures 真实路径但函数名/行号须占位、
   不得等于 `primary_anchor` 真实答案；
3. `public_constraints` 要求"单个 JSON 对象、top-1、完整函数、不返回候选列表"，并
   **不出现**任何 oracle 私有字段名；
4. 用 `primary_anchor` 填一份合规样例，验证（未来）grader 能映射到 score=1；
5. （退化解防护）若已实现 grader（M7），在其中加规则：提交 span 字节数远大于
   `role_oracle` 最大条目 → 按 0/`ambiguous` 处理；部分重叠多条但不完全包含 → 按
   `ambiguous_name` 处理；括号不平衡 → 非法提交。

**落地位置**：`agent_visible/task.json`（+ M7 的 grader）。
**done 条件**：审查报告 A6 全 PASS；§8 泄漏检查无命中。

### M5 console 可观测性修复（触发：审查 §5.1 / §12.3 / §10.12）

**问题**：`task.json`/README 承诺"submit 后 console 出现某 field"，但人手按步骤操作
**看不到 log**（gate 没开、sink 没执行、verify 监听过宽/过窄、interaction 与 verify
不一致、build 产物与 captures 不一致）。

**改动内容**：
1. 对齐 `task.json: interaction[]` 与 `verify.mjs` 的操作序列（顺序/selector/value）；
2. 沿 `src/` submit 路径确认 sink 处确有对该 field 的 `console.log`（或等价 observable），
   且 `interaction[]` 能走到该路径、gate 能被打开；
3. `verify.mjs` 用 `page.on('console')` 等价机制，`targetPromise()` 等待**与题面一致**
   的 action/field/value 模式（不是测了别的字段或更宽松子串）；
4. 实测：`node scripts/verify.mjs`（或 smoke 浏览器）确认目标 log 出现，记录样例行。

**落地位置**：`agent_hidden/src/**`（sink/gate）、`agent_hidden/scripts/verify.mjs`、
必要时 `task.json`。
**done 条件**：审查报告 **A5** 实测出现题面所述 log；§5.1 / §12.3 全 PASS。

### M6 全英文改写（触发：审查 §2 / §10.9）

**问题**：构成 case 的内容（尤以 `task.json: question`）含中文等非英文——硬性违规，
"中文题面+英文约束"双语组合本身不合规。

**改动内容**：把审查报告 B 类列出的每条非英文片段改写为英文，范围含 `task.json`、
`README.md`、`src/**` 注释/字符串/`console.*` 文本、`oracle`/`build_meta` 自然语言
字段、`scripts/*` 注释。例外：`*_postmortem.md` 内部笔记可不改但注明。改写
`question` 时**不要**把通用 anchor 定义塞进每个 `question`——走 M12 共享机制防漂移。

**落地位置**：命中的各文件。
**done 条件**：审查 §2 全英文扫描无命中，B 类清空。

## 3. P1 修改项

### M7 实现可执行 grader（触发：审查 §6.6 / §13 / §10.15）

**问题**：评分语义只写在 `oracle.hidden.json`（`score_values`/`role_oracle`/
`scoring_policy`/`scoring_examples`），仓库内**通常没有** `grade_submission.mjs`；
`verify.mjs` 不评 agent 答案。这使"agent 答案 → 分数"不可复现（缺 SWE-bench 式
可执行 FAIL_TO_PASS）。

**改动内容**：新建 `agent_hidden/scripts/grade_submission.mjs`，按 `审查.md` §13.2
算法实现：
1. 解析 agent 提交（`task.json: answer_format.response_schema`）；
2. 在 captures bundle 按 `slice.offset` 重切片，校验完整函数体（可选 hash）；
3. 按 `scoring_policy.span_overlap_policy` 在 `role_oracle` 找唯一命中行；
4. 取命中行 `score`/`role`/`answer_function`；辅判 `function_name===answer_function`；
5. 无唯一命中 → 0；并实现 M4 的退化解规则；
6. 自定义输出 schema（如 `{score, role, answer_function, matched_span, reason}`）——
   仓库未统一规范，勿臆造 `match_basis` 等不存在字段。
导出纯函数 `gradeAnswer(submission, oracle, capturesRoot)` 供仓库级批量评测复用。

**落地位置**：`agent_hidden/scripts/grade_submission.mjs`、`package.json` 加 `"grade"`。
**done 条件**：用 `primary_anchor` 标准答案得 1.0、nested helper 得 0.7、off-chain 得 0、
超大 span 按 M4 规则扣分；审查 §6.6 / §13 由"仅声明式"转为"有可执行实现"。

### M8 移除基础设施填充；行数门槛只针对 `src/`（触发：审查 §3.2 / §10.8）

**问题**：`README.md` 数百行 `readme-row`、`package.json` 的 `local_notes`、
`scripts/*.mjs` 末尾未引用的 `const verify_N=…^N` 死代码——为凑行数门槛注入的无关
填充，浪费 agent token、掩盖真实逻辑、使"行数要求"失去意义。

**改动内容**：
1. 删除上述所有无关填充行/字段/死代码；
2. 把 `build.mjs`/`verify.mjs` 的 `requirements` 行数/体积门槛改为**只统计 `src/`**
   手写内容，基础设施文件不设行数下限（或下限=诚实写完的自然长度）；
3. 若确需更大 bundle 体现 vendor noise，改为在 `src/z0/x|v` 等诱饵池**手写更多真实
   诱饵模块**（语法正确、被 oracle/build_meta 计数），而非构建期机械注入。

**落地位置**：`README.md`、`package.json`、`scripts/*.mjs`、必要时 `src/`。
**done 条件**：审查 §3.2 无命中，报告 C 类清空。

## 5. M12 Prompt 改进：Anchor 通用判定规则 + One-shot 示例

> 目标：让每个 case 的 `task.json: question` 对"anchor function"的说明与 `论文.tex`
> 的 Problem Definition（约 270–282 行的 anchor 规则形式化）一致，并补一个基于论文
> motivating example（约 150–237 行；对应 `sage-checkout-case/task.md` 的
> `order_sig_v2` checkout 场景）的 one-shot 推理示例。这是一项**跨 case 统一的 prompt
> 改进**，与 `审查.md` §12.4（提交格式）正交、不冲突。

### 5.1 现状（以 case001_browser_fingerprint 为例）

`task.json: question` 目前只给出**针对本 case 类别（browser fingerprint）的具体化
定义**（"the first target-specific browser fingerprint value constructor … rather than
merely collecting raw navigator/screen/canvas features, dispatching control, …"）。
这是论文 anchor 规则在该类别上的**实例化**，但缺两样论文原文有、当前 prompt 没有的
东西：
1. 论文的**通用判定规则**（target-specific / generic 的可操作定义、"anchor=链上最浅
   的、直接调用者为 generic 的 target-specific 函数"、消歧三情形 Case 1/2/3）；
2. 一个**跨领域的 worked example**（one-shot），让 agent 先在抽象链路上学会应用规则。

`answer_format.example` 现有的占位示例只是**输出格式样例**，不是推理示例，二者互补、
应同时保留（且 example 须遵守 `审查.md` §12.4 的不泄漏要求）。

### 5.2 新增内容 A：通用 Anchor 判定规则（译自论文 Problem Definition）

> General rule for resolving ambiguity: a function is **target-specific** with
> respect to the observable described above if at least one statement in its body
> either constructs/binds the target value, writes the target field, or dispatches
> the target action — and removing that statement would break the observed target
> output under the prescribed interaction. A function is **generic** if it is a
> reusable utility (hash/encode/serialize/normalize/collect-features), a
> control-flow dispatcher (router/interceptor-pipeline/event-bus/scheduler), or a
> preparation routine (validate input/collect UI state/lifecycle hook) whose body
> would look the same regardless of which behavior it currently serves.
>
> The **anchor** is the unique target-specific function on the chain whose
> immediate caller is generic — equivalently, the *shallowest* target-specific
> function on the path from the trigger to the sink. Three situations commonly
> cause confusion:
> - If a target-specific function `C` is called by a generic dispatcher `B` and
>   itself calls a generic utility `D` (e.g. a hash routine), the anchor is `C`,
>   not `B` (too generic/upstream) and not `D` (too generic/reusable).
> - If a generic function `A` merely writes whatever its callee `B` returns into
>   the target field, and `B` is the function dedicated to computing that value,
>   the anchor is `B`, even though the literal field assignment is syntactically
>   inside `A`.
> - If the target-specific statement is just one branch/line inside a larger
>   function `F` that also handles unrelated cases, `F` is still target-specific
>   and remains a valid anchor candidate — do not discard it for a "purer" sub-fn.

### 5.3 新增内容 B：One-shot worked example（译自论文 motivating example）

> Worked example (different scenario, for illustration only): A checkout page
> emits `body.order_sig_v2` after the user clicks "Submit Order". The runtime chain:
>
> ```
> click Submit Order
>   -> construct order draft                 (generic: prep/state collection)
>   -> encode checkout state                  (generic: prep/state collection)
>   -> collect async profile receipt          (generic: prep/state collection)
>   -> compose request envelope               (generic: prep/state collection)
>   -> run interceptor pipeline               (generic: dispatcher)
>   -> select sealing interceptor             <-- ANCHOR
>   -> canonicalize payload fields            (nested helper, target-specific)
>   -> fold payload with receipt + pepper     (nested helper, target-specific)
>   -> compute digest                         (core utility: generic SHA-256)
>   -> write body.order_sig_v2
>   -> send request                           (wrapper/sink: generic)
> ```
>
> The **sealing interceptor** is the anchor: its immediate caller is the generic
> interceptor-pipeline dispatcher; its own body is the highest point on the chain
> whose code, read alone, explains why `order_sig_v2` specifically is produced (it
> assigns the final signature into the request envelope). Functions below it
> (canonicalize, fold) are nested helpers (0.7); the digest routine is a core
> utility (0.5); dispatcher and request sender are path/wrapper (0.2 each). Other
> same-click values such as `analytics_sig`, `coupon_digest`, `view_cache_key`,
> `retry_fingerprint` are off-chain decoys (0). Apply the same reasoning to the
> actual page and bundle below.
