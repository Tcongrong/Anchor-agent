# Benchmark Case 结构审查提示词（Structural Design Audit）

> **本文件只负责"审查"——发现并分类问题；所有"怎么改 / 迁移步骤 / 待实现 grader /
> 待补 schema / prompt 改进"等可执行修改动作，统一收敛到配套的
> [`修改.md`](修改.md)。** 固定流程为**先审查、再修改**：
> 1. 先用本文件（§0–§15）逐项审查 `benchmark_cases/<case_id>/`，产出
>    `<case_id> 结构审查报告`（§9 格式）；
> 2. 再拿报告里被标 BLOCKING / WARN 的条目，到 `修改.md` 找对应修改项（M1–M12，
>    每项注明由本文件哪一节触发）执行。
>
> 即：本文件回答"**哪里有问题、多严重**"，`修改.md` 回答"**具体改什么、改在哪、
> 改完怎样算通过**"。本文各节内嵌的"正确做法 / 修复方向"短注仅用于帮助判级；其
> 可执行、带优先级与 done 条件的版本以 `修改.md` 为准。

> **⚠️ 审查重中之重（最高优先级，零容错）**：本审计里**最重要、最不能出错**的，是
> **答案集（oracle）的正确性**。具体为三问，缺一不可：
> 1. **答案集本身是否正确**：`primary_anchor` 与**每一条** `role_oracle` 的
>    角色/分值/坐标，是否真的对应它们所声称的那个函数——即**轨 B 语义正确**，而非
>    仅 hash 自洽（hash 44/44 + verify 绿 **不能**代替本检查，见 §10.6）。
> 2. **是否能匹配到正确函数**：`captured_span` 切片是否**完整且唯一**地命中目标源
>    函数；多同名（多个 `r` / `keyRing`）是否两两不混、offset 各异；agent 的合规
>    提交能否被 grader **唯一**映射到正确档位（见 §4.1.4、§12.1–12.2）。
> 3. **是否真实存在于 captures 中**：每条答案/诱饵函数是否能在
>    `agent_visible/captures/` 的 bundle 里**按坐标真实切出**（**全部条目，禁抽样**，
>    且对 captures 原文重算 hash，不得复读 oracle 里的 hash 字符串）。
>
> 这三点对应 **§4.1（含 §4.1.3–4.1.5）+ §12.1–12.2**，**任一失败一律 BLOCKING**；
> 其余章节即便全部 PASS，只要这三点有一条未亲自核实，本次审查即视为**未完成**，
> 不得给出"整体通过"结论。

## 0. 审查边界声明

你正在审查 `benchmark_cases/<case_id>/` 这一个 benchmark instance 的**结构完整性**，
而不是其混淆代码的具体语义或题目难度是否"出得好"。
你的目标只有一句话：**task（题面）→ answer（oracle 金标准）→ verify（自动校验）这三者
能否在不依赖人工脑补的情况下精确对上**，以及围绕它们的文档/脚本是否干净、可复现、
未泄漏答案。

本提示词遵循以下硬性前提（贯穿全部章节）：

1. **全英文**：构成本 case 的全部内容（题面、文档、注释、隐藏元数据的自然语言字段等）
   必须是英文，中文/其它语言一律视为违规——详见第 2 节。
2. **噪声分区**：噪声/填充/诱饵内容**只允许**作为 `agent_hidden/src/`（题目本身）的
   设计要素存在；`agent_visible/task.json`、`agent_hidden` 下基础设施与文档文件中不允许
   出现与任务无关的填充——详见第 3 节。
3. **Captures 真实性**：oracle 给出的全部答案/角色/诱饵函数必须能在
   `agent_visible/captures/` 中
   真实定位、校验，且 `captures/` 必须真实对应本 case 当前的网页与 bundle——详见第 4 节
   （**重要**）。
4. **Span 语义正确性**：oracle 坐标的 hash 自洽**不等于** span 语义正确——必须验证
   提取片段是**完整函数体**、**映射到正确源函数**、**不同源函数不得错误合并**——详见
   第 4.1.3–4.1.5 节与第 10 节。
5. **Anchor 唯一明示**：每个 case 必须能**无歧义**回答"anchor 到底是哪一个函数"——
   见第 12.1 节。仅有一段自然语言 `anchor_definition`、或只有模糊的
   `role_oracle` 而无明确 `primary_anchor`，均不合格。
6. **Agent 可见边界极窄 + 物理目录分区**：参赛 Agent **只能**读 `agent_visible/`
   下的 `task.json` 与 `captures/`（以 `answer_format.visible_corpus` 为准）。
   维护者/私有材料**必须**放在 `agent_hidden/`，**不得**与 agent 材料混放在 case 根目录
   或同一扁平目录——见第 12.4–12.5 节。**canonical 参考布局**：
   `case001_browser_fingerprint/`。
7. **标准答案以 captures 为准（grader 侧 `answer_function`）**：Agent 在 bundle 里看到
   什么函数名就提交什么（`task.json: function_name`）；不可能知道 `src/` 源侧名。
   Oracle 用 `primary_anchor.answer_function` + `captured_span` 作 grader 金标准；
   `source_function` 仅供维护者/gen——见第 12.2 节。**禁止**把 `source_function` 当作
   agent 应答或 grader 主判据。
8. **Agent 提交格式须在 task.json 明示**：`answer_format.response_schema` 必须规定
   agent 输出的 JSON 结构（`function_name` + `slice`），并与 oracle 坐标可对齐——见第
   12.4 节。
9. **运行时 console 可观测**：`task.json` 若声明目标值出现在 `console.log`（或类似
   sink），则**真实网页按题面交互后必须能观测到该输出**——见第 12.3 节。
   `verify.mjs` 通过不能代替人工/脚本对 console 的实测。
10. **关键文件组织以 canonical case 为准**：审查其它 case 时，目录布局、关键文件位置、
    `task.json` 提交 schema、`oracle` 双轨命名（`answer_function`/`source_function`）、
    脚本路径约定，**一律以 `case001_browser_fingerprint/` 为标杆**；不符合者审查须判
    **BLOCKING** 并在修改时迁移对齐——见第 14 节。

## 0.1 Agent 审查态度与执行纪律（硬性要求：必须事无巨细、足够认真细致）

你不是在写"看起来合理"的摘要，而是在做**可阻断发布的结构审计**。以下纪律贯穿全部章节，
违反任何一条都可能导致"报告写得很长、但核心 bug 仍漏掉"——这在
`case001_browser_fingerprint` 的实战复盘里已被证明会发生。

### 必须做到

1. **先读全、再下结论**：第 0 节列出的文件必须**完整读取**；`oracle.hidden.json` 的
   `role_oracle` **每一条**都要单独核验，禁止"抽 2–3 条代表通过"。
2. **双轨验证，缺一不可**：
   - **轨 A（坐标自洽）**：按 `captured_span` 切片重算 hash，与 oracle 记录比对；
   - **轨 B（语义正确）**：切片必须是完整语法单元，且对应**正确的源函数/角色**——仅
     轨 A 通过而轨 B 失败，仍判 **BLOCKING**。
3. **用 bundle 原文举证**：每个 BLOCKING 必须附带从 `captures/.../account.app.bundle.js`
   （或对应文件）**实际切出的片段**（至少首尾 80 字符 + 字节长度 + 起止行号），不得
   只说"hash 匹配"或"脚本 exit 0"。
4. **主动重跑工具链**：若存在 `scripts/gen_oracle_spans.mjs`、`scripts/verify.mjs`、
   `npm run build`，审查时必须**实际执行**并记录输出；不得仅凭静态阅读推断"应该能通过"。
5. **追查根因，不止于表象**：发现不一致时，继续追问是模板克隆未同步、`captures/` 过期、
   `gen_oracle_spans` 解析 bug、还是混淆后命名碰撞——并在报告中写明因果链。
6. **对"已通过"保持怀疑**：`verify.mjs` 通过、`hash 44/44`、脚本 `exit 0` 均不能替代
   第 4.1.3–4.1.5 的语义审查；历史上这些指标曾与错误 span **同时成立**。
7. **逐项打勾留痕**：建议维护内部核对表（不必写入报告正文），至少包含：
   `role_oracle` 条目序号 1..N 每条是否完成 4.1.1–4.1.5；`primary_anchor` 是否单独复核；
   所有同名/异名 `r` 是否 span 两两不同；`gen_oracle_spans` 是否存在且可成功运行。
8. **实测 console 输出**：除跑 `verify.mjs` 外，必须按 `task.json: interaction[]` 在
   浏览器或 Playwright 中**亲自走一遍**（或阅读 verify 的 `scenario()` 并确认其监听
   逻辑真的能捕获输出）——历史上出现过 verify 通过但人手测试无 `console.log` 的 case。
9. **填写 Anchor 身份卡**：报告必须包含第 9 节 **A4**，写死 anchor 是谁——
   **`answer_function`（grader 标准名，= agent 在 bundle 里应提交的 `function_name`）**、
   bundle 切片起止、`source_function`（私有映射）、唯一性结论。
10. **区分 Agent 轨 / Grader 轨 / 维护者轨**：审查与文档中不得把 `build_meta`、
    `oracle`、`score_values` 混进"agent 怎么做题"的描述——见第 12.4、第 13 节。
11. **目录分区与 canonical 对齐**：审查时先核对 `agent_visible/`/`agent_hidden/`
    是否存在且内容正确；修改 case 时**优先**按 `case001_browser_fingerprint` 重组，
    而非在旧扁平布局上打补丁——见第 12.5、第 14 节。

### 严禁做法（实战复盘中的真实漏审模式）

| 漏审模式 | 为什么危险 | 正确做法 |
|---|---|---|
| 只验 hash 自洽，不验切片是否完整函数 | 错误切片也能算出"正确"hash 并写回 oracle，形成自洽闭环 | 4.1.3 完整性 + 人工读切片 |
| 只验 `primary_anchor`，抽样其它条目 | 非 anchor 条目错位会直接导致 grader 误判 | 全部 44+ 条目逐条验 |
| 见 `verify.mjs` 通过即宣告 case 合格 | verify 不测 span 语义，不测 oracle 生成逻辑 | 必须叠加 4.1.3–4.1.5 |
| 见 `gen_oracle_spans` exit 0 即信任 | 脚本自身可能有 bug，exit 0 只说明"写盘成功" | 读脚本逻辑 + 跑后做独立审计 |
| 不读 `gen_oracle_spans.mjs` 实现 | 解析 bug 是 span 错位的首要根因 | 第 11 节专项审查 |
| 把"歧义/未解析"当脚本问题忽略 | 未解析条目意味着 oracle 不完整 | 未解析 = BLOCKING |
| 不区分 `captures/` 与 `dist/` 绑定关系 | 改 src 后 oracle 可能静默失效 | 第 7 节 + 实际 build 验证 |
| 把 `build_meta`/`oracle` 当 agent 可见信息 | agent 根本读不到，审查结论会误导 | 第 12.4 节三分轨模型 |
| 在题面/require 里要求 agent 输出 `answer_function` 等 oracle 字段名 | agent 不应知道私有 schema | 题面只用 `function_name`+`slice` |

### 细致程度底线

- 一个 case 的完整结构审查，应能在报告中回答：**每一个** `role_oracle` 条目"切出来
  是什么、为什么是它、与其它条目有何不同"。
- 若 case 存在多个同名函数（如 8 个不同的 `r`、两个 `keyRing`），必须**逐一列出**
  其 `sourceKey → source_function → answer_function（bundle 切片行首名）→ offset 范围`
  映射表，并确认无错误合并。
- 若你不确定，标为 `UNVERIFIABLE` 并说明缺什么证据——**禁止**用"大概没问题"带过。

## 2. 全英文检查（硬性要求：case 内容必须全英文）

**规则**：构成本 case 的全部"案例内容"——即会被 agent 读取、或被 `build.mjs`/
`verify.mjs` 处理、或作为评测依据的所有文本——必须使用英文。这不是风格建议，而是
结构性硬性要求；任何非英文片段都应作为违规列出，**无论是否"看起来是有意为之的双语
设计"**。

需要逐一检查的范围：
- `task.json`：`question`、`public_constraints`、以及其它任何字符串字段；
- `README.md` 全文；
- `package.json` 中的描述性字段；
- `src/**`（含 `src/host/*.html|css`、`src/z0/**/*.js`）中的注释、字符串字面量、
  `console.*` 输出文本、错误信息等——这些内容可能在混淆后仍以可读形式留在
  `captures/` 的 bundle 中，被 agent 直接看到；

  `anchor_definition`/`oracle_notes` 等自然语言字段；

**例外**：纯内部开发笔记（如 `*_postmortem.md`）不计入本规则，但仍应在报告中注明其

**检查方法**：对上述每个文件做一次"非 ASCII / 非英文字符"扫描（中文、全角标点等），

## 3. 噪声/填充内容检测：题目内（`src/`）允许，题目外（基础设施）禁止

**前提区分**：
- **"题目内"** = `src/**`（含 `src/host/**` 静态资源与 `src/z0/**` 全部业务/诱饵/噪声
  代码）。这些文件的体量、诱饵、看似无意义的辅助代码是题目设计的一部分（混淆、
  distractor、semantic decoy 等），**不应**仅因为"看起来像填充"就被判为问题。
- **"题目外"（基础设施/文档）** = `task.json`、`README.md`、`package.json`、
  `scripts/build.mjs`、`scripts/verify.mjs`、`scripts/serve.mjs`、
  `build_meta.hidden.json`、`oracle.hidden.json`。这些文件描述/驱动/记录这个 case，
  其内容应 100% 服务于这一目的。

### 3.1 题目内（`src/`）—— 检查"噪声是否被正确纳入题目设计"，而非是否存在

对 `src/` 下的诱饵/噪声/大体量模块，检查：
1. 它们是否在 `oracle.hidden.json: role_oracle` 中有对应条目（角色为 `Off-chain`/
   `Path-generic-helper` 等），或被 `build_meta.hidden.json` 的
   `distractor_count`/`semantic_decoy_count`/`submit_path_decoy_count` 等数字计入？
   - 若某个明显是"批量生成的相似模块"（如 `src/z0/x/x00.js` ~ `x43.js`、
     `src/z0/v/v00.js` ~ `v24.js`）**完全没有**被 oracle/元数据提及或计数，需指出
     "存在游离于设计意图之外的噪声代码，oracle 覆盖不完整"（与第 4.1 节呼应）。
2. 这些噪声模块本身是否仍是**语法正确、风格一致、看起来像真实业务代码**的内容，而
   不是机械占位符——即便是"为了凑总行数"，题目内的凑法也应该是"多写几个像样的诱饵
   函数/路由表项"，而不是无意义的重复模板。

### 3.2 题目外（基础设施/文档）—— 任何无关填充都是结构性缺陷

逐文件检查是否存在为满足 `build.mjs`/`verify.mjs` 的 `requirements` 行数门槛而注入的、
与任务描述/构建/校验逻辑**无关**的内容，包括但不限于：
- `README.md` 中循环重复、仅索引递增的行（如
  `readme-row 0NN: deterministic local benchmark detail N.`）；
- `package.json` 中的 `local_notes`/`entry_00X` 之类占位字段；
- `scripts/build.mjs`/`scripts/verify.mjs` 文件末尾大段未被引用的
  `const verify_N = (...) ^ N;`/`const build_N = ...` 死代码；
- `oracle.hidden.json`/`build_meta.hidden.json` 中任何明显模板化重复、与本 case
  实际内容无关的字段或注释。

**判定**：以上任何一处都应报告为 **必须移除的结构性缺陷**（不是"代码质量建议"），
并在第 9 节报告中单独成类。同时评估：`requirements` 表中对该文件设置的行数下限本身
是否就是诱发填充的根源——若是，建议将"行数复杂度"指标改为只针对 `src/`（题目内容）
统计，基础设施文件不设行数下限，或下限应等于其"诚实写完所有必要内容"所需的自然
长度。

## 4. Captures 真实性与对应性检查（重要）

本节是整套审查中最关键的部分之一：`captures/` 是 agent 唯一能看到的代码语料，也是
`oracle.hidden.json` 全部坐标的基准。如果 `captures/` 本身有问题——答案/诱饵不在
里面，或者根本不是这个 case 的页面——后面所有"打分逻辑是否自洽"的讨论都没有意义。

### 4.1 答案集合（含全部评分档位与诱饵函数）是否真实存在于 captures 中

对 `oracle.hidden.json: role_oracle` 中的**每一条记录**（覆盖 `score_values` 的所有
档位：1 / 0.7 / 0.5 / 0.2 / 0.1 / 0(Off-chain)，**不只是 `primary_anchor`**），逐条
执行：

1. **文件存在性**：`captured_span.file` 指向的路径是否真实存在于
   `captures/devtools-source-dump/`？
2. **跨度可提取且哈希一致**：按 `start_offset`/`end_offset`（或
   `start_line`/`end_line`）从 **`captures/` 内真实 bundle 文件**提取字节切片，
   重新计算 `sha256`/`normalized_sha256`，必须与记录值一致。**禁止**用 oracle JSON
   里已有的 hash 字符串做"复读式"验证。**这一步要对全部条目做，不能只抽样 2-3 条**
   ——抽样只能发现"系统性错位"，无法发现"个别条目错位"。
3. **片段是完整且对应的语法单元（轨 B 核心，不可省略）**：提取出的内容应是一个
   **完整**的函数/方法体（不是被截断的半个函数），且其内容应与该条目的
   `answer_function`（bundle 切片行首名，agent 可见标准答案标识）、`role`、`why`
   描述在语义上能对上。对**每一条**（含 `primary_anchor`）必须同时检查：
   - 以 `function <name>(` 开头（或该 case 允许的等价导出形式）；
   - 以匹配的 `}` 结尾，大括号层级平衡；
   - **函数体**在第一个参数列表 `)` 之后——不得把默认参数里的 `s = {}`、解构默认值
     等误当作函数体起点（见第 10.1 节）；
   - 字节长度合理：`primary_anchor` 不得仅为签名行（历史上曾出现 ~48B 截断）；
   - 片段内应含可核对的逻辑痕迹（位运算、`return`、关键调用、字符码数组、诱饵字段
     构造等），而非只有函数头。
4. **针对 `Off-chain`（诱饵）条目的额外检查**：
   - 该诱饵函数在 bundle 中是否**可达**（被调用、被注册为事件处理器、或出现在某个
     路由/分发表中）？如果是完全孤立、不可能被执行到的死代码，那么 `verify.mjs`
     中"运行时会产出诱饵输出"一类断言（如 `decoy_outputs_not_target`）以及题面
     `public_constraints` 中"会出现诱饵字段"的描述就缺乏运行时基础，应报告为不
     一致。
   - `task.json: public_constraints` 中点名的诱饵字段（如 `device_hash`、
     `browser_trace`）能否在对应 Off-chain 函数体内找到字符级证据（哪怕是混淆后
     的字符码数组形式）？

任意一条记录在上述任一步骤失败，都判定为 **BLOCKING**：表示私有 oracle 与公开语料
`captures/` 已脱节——要么 agent 永远定位不到该角色对应的代码，要么该角色在评分时
永远不会被正确命中。

#### 4.1.3 独立语义审计（禁止用 hash 自洽代替）

在完成 4.1.2 的 hash 核对后，**必须**额外执行以下检查（建议写一次性审计脚本或手工
逐条核对，并保留输出）：

1. **完整函数体**：对 `primary_anchor` 及所有 Path-critical / Anchor 条目，报告
   `end_offset - start_offset` 字节数与行数；若 anchor < 100 字节或仅 1 行，几乎必为
   截断，判 BLOCKING。
2. **切片首尾举证**：每条至少记录 `slice.trim().slice(0,80)` 与 `slice.trim().slice(-40)`，
   证明不是空壳签名。
3. **源侧对照**：读取 `source_file` 中对应函数源码，与 bundle 切片做**结构级**对照
   （参数个数、是否 async、大致控制流），而非仅比函数名。

#### 4.1.4 同名异源函数不得错误合并（多 `r` / 多 `keyRing` 专项）

若多个 `role_oracle` 条目映射到**不同源文件**的**同名函数**（典型：`r`、`keyRing`），
必须：

1. 列出全部此类条目的 `sourceKey`（`文件::函数名`）与 `captured_span` 的
   `start_offset-end_offset`；
2. 确认**不同 sourceKey 的 span 两两不同**——除非已验证源函数体逐字相同且混淆后
   确实同一实现（需在报告中显式说明理由）；
3. 对 bundle 中每个候选实现，核对 oracle 中 `answer_function`（如 `r$d`、`r$c`、`r$1`、
   `r$e`、`keyRing$1`）是否与源文件语义一致，而非全部落到同一个 `export function r`；
4. 每条 oracle 记录应含 `answer_function`（从 bundle 切片提取）与 `source_function`
   （源侧私有映射）；**禁止**仅写 `function`/`bundle_function` 等遗留字段而让 agent
   误以为标准答案是源侧名。

**历史事故**：8 个不同 `r` 曾被写成同一 span `1064031-1065138`，hash 仍 44/44——
这是典型的"轨 A 通过、轨 B 失败"。

#### 4.1.5 `gen_oracle_spans` 生成结果不得盲信

若 case 含 `scripts/gen_oracle_spans.mjs`（或等价脚本）：

1. 审查时必须**阅读脚本实现**（第 11 节）并**实际运行**；
2. 运行成功（exit 0）后仍须做 4.1.3–4.1.4；
3. 脚本若只报 `hash_verified: N/N` 而无完整性/去重校验，应在报告中标注
   **"生成器自检不足"** 为 WARN，并建议补强。

### 4.2 captures 是否真实对应"本 case 构造出来的网页"

`captures/` 应该是对**本 case** `dist/`（由当前 `src/` 通过 `build.mjs` 构建）所渲染
页面的一次真实抓取，而不是遗留自其它 case/模板的快照。逐项核对：

1. **页面标识**：`captures/.../index.html` 的 `<title>` 是否与
   `scripts/verify.mjs` 中 `page.title() === '...'` 的断言值、以及
   `src/host/index.html` 当前内容一致？
2. **DOM 控件**：`task.json: interaction[]` 用到的全部 selector（如
   `#probeAlias`、`#armSurface` 等）是否能在 `captures/.../index.html` 中找到
   对应元素？元素上的关键 `data-*` 属性（如 `data-scan="fp:44:9"`）是否与
   `verify.mjs` 中的断言、`build_meta.hidden.json` 中的难度数字（如
   `route_table_rows: 44`）一致？
3. **bundle 引用路径**：`captures/.../index.html` 中引用的脚本路径是否与
   `dist/index.html` 一致（如 `assets/account.app.bundle.js`）？
4. **bundle 内容的 case 特异性**（**注意混淆后名称变化，见第 12.2 节**）：
   - **允许**：源侧函数名（如 `assembleBrowserFingerprint`）在混淆 bundle 中**已改名**
     或仅部分残留——此时应以 `captured_span` 坐标 + 切片语义 + case 特异常量
     （如 `data-scan` 值、`surface:delegate`、`fp:44:9` 等）判断 captures 归属；
   - **禁止**：因 bundle 里 `grep` 不到 `primary_anchor.source_function` 就判 captures
     无效——agent/grader 的标准答案是 `answer_function` + `captured_span`，不是源侧名；
   - **仍须检查**：`task.json`/`verify.mjs` 用到的 DOM selector、`data-scan`、页面
     title 等**未混淆或半残留**的锚点是否能在 captures 页面中找到；目标 observable
     的 **action/field 名字面量**（常经字符码数组残留）能否在 sink 路径上找到证据。
5. **时间线合理性**：`captures/devtools-source-dump/manifest.json: captured_at`
   与本 case 其它时间/版本痕迹（如该 case 是否明显由其它 case 改造而来）相比，是否
   存在"captures 的抓取时间早于改造发生时间"这类矛盾——若有，说明 `captures/` 从未
   基于改造后的 `src/` 重新生成过。

任意一项不一致，均判定为 **BLOCKING**：意味着整个 oracle 可能建立在错误的语料上。
**这是排查"build_meta.hidden.json 的 trigger 与 task.json 不一致"这类问题根源的
关键一步**——如果 4.2 的检查发现 `captures/` 本身就是旧模板的快照，那么不只是
`build_meta.hidden.json`，`oracle.hidden.json` 的坐标也可能需要整体重建。

## 5. Task–Answer–Verify 三角精确匹配

这一节聚焦"逻辑层面"的精确匹配（坐标/哈希层面的真实性已在第 4 节核验，此处不重复）。
目标：回答"如果 agent 给出了 `primary_anchor` 对应的函数作为答案，评分逻辑能否在不
依赖人工判断的情况下确认它是对的；如果给出别的函数，能否被正确按 `score_values`
打分？"

1. **可达性**：`primary_anchor.captured_span.file` 及全部 `role_oracle` 条目的文件
   路径，是否都落在 `task.json: answer_format.visible_corpus`（或
   `build_meta.hidden.json: candidate_scope.included`）声明的 glob 范围内？

2. **唯一性/重叠消歧**：是否存在多个 `role_oracle` 条目的 `captured_span` 互相重叠/
   嵌套？`scoring_policy.span_overlap_policy` 描述的规则是否足以处理"agent 给出一个
   同时覆盖 anchor 与其某个 nested helper 的更大函数"这类场景，推演后打分是否唯一
   确定？

3. **observable 判定与 verify 实现一致**：`verify.mjs` 中判定"目标输出"的代码
   （action/field 名、格式正则）是否与 `task.json: observable`/`answer_format` 及
   `oracle.hidden.json: target_reference` 完全一致？

4. **诱饵声明与实现一致**（与 4.1 第 4 点呼应）：`public_constraints` 中提到的诱饵
   字段名是否与 `verify.mjs` 中实际产生/校验的诱饵字段一致？

5. **bundle 内"答案痕迹"检查（混淆友好，勿与源侧函数名混为一谈）**：
   `verify.mjs` 中 `bundle_contains_answer_code` 一类检查，应使用**混淆后仍可能残留**
   的证据（特异字符串、字符码序列、DOM 事件名、路由表项如 `fp:44:9`），**不应**
   要求 bundle 内仍存在 `primary_anchor.source_function` 的源侧标识符字面量——否则与
   第 12.2 节冲突（**标准答案应是 `answer_function`，不是 source_function**）。审查时
   判断：该正则是在验混淆后仍可能残留的路径特征（合理），还是在验源侧函数名（应改为
   `answer_function` 或结构特征）。若 verify 因源侧名搜不到而 FAIL，但 `answer_function`
   与 span 正确，应报告 **verify 待修复**。

6. **anchor 的"第一性"可验证性**：`anchor_definition` 通常包含"第一个...的函数"这类
   排他性表述。`role_oracle` 中是否存在调用顺序早于 `primary_anchor` 但同样满足
   "构造目标值"描述的条目？若存在，需给出推理依据说明"第一个"判定为何仍唯一成立。

7. **Agent 提交 JSON ↔ Oracle 坐标可对齐**（对应第 12.4 节，**BLOCKING**）：
   - `task.json` 是否含 `answer_format.response_type: "json"` 与完整 `response_schema`；
   - agent 字段 `function_name` 是否明确为 **captures bundle 切片行首名**（非源侧名）；
   - agent 字段 `slice.{start_line,end_line,start_offset,end_offset,code}` 是否与
     `captured_span` 同构，且 `code` 要求完整函数体；
   - 用 `primary_anchor` 填一份合规 agent 提交样例，验证 grader **能**映射到 score=1；
   - **禁止**在 `task.json` 里引用 `answer_function`/`source_function`/`captured_span`
     等 oracle 私有字段名作为 agent 必填 key。

每一条给出 `PASS`/`FAIL`/`UNVERIFIABLE`，FAIL 一律视为 BLOCKING。

**特别说明（verify 能力边界）**：`scripts/verify.mjs` 通常验证运行时行为、bundle 存在性、
泄漏边界等，**一般不验证** `role_oracle` 每条 span 的语义正确性。因此
**verify 通过 ≠ oracle 坐标正确**（见第 10.6 节）；第 5 节 PASS 不能替代第 4.1.3–4.1.5。

### 5.1 运行时 Console 可观测性（硬性，对应第 12.3 节）

若 `task.json` 的 `observable` / `public_constraints` / `answer_format` 表明答案出现在
浏览器控制台（典型：`action` + `field` 的 JSON/log 行），则必须**全部**满足：

1. **Verify 真测**：`verify.mjs` 在按 `interaction[]` 驱动页面时，有 `page.on('console')`
   或等价机制，且 `targetPromise()` 等待的是**与题面一致**的 action/field/value 模式——
   不是测了别的字段或更宽松的子串就判通过。
2. **人工复现**：审查 agent 必须实际执行 `node scripts/verify.mjs`（或 `npm test`），并
   在报告中记录：是否观测到目标 log、样例输出长什么样。若 verify 通过但题面描述的
   log **人手无法复现**，判 **BLOCKING**。
3. **Trigger 可达**：沿 `src/` 追踪 submit 路径，确认 sink 处确有 `console.log`（或
   经包装后的等价输出），且 `interaction[]` 的点击/输入序列能走到该路径——不是死路由、
   不是 gate 永远为 false、不是仅写 `node.value` 而无 log。
4. **与诱饵区分**：`public_constraints` 若说"会有其它 console 输出"，verify 的
   `decoy_outputs_not_target` 与主题目 log 的判定边界是否清晰，避免"有任意 log 即通过"。

**历史问题**：存在 case 在自动化脚本 green 的情况下，开发者按 README 操作却**看不到**
题面所指的 `console.log` 结果——属于 task–verify–实现 断裂，必须 BLOCKING。

## 6. Oracle 内部评分体系自检

1. 列出 `score_values` 的全部 key 与数值，标出**数值重复但 key 名不同**的项
   （例如 `Path-critical` / `Path/Wrapper` / `Wrapper` 都=0.2）。对每一组重复，
   判断：① 是否本应代表不同档位但被错误地赋了相同分值；② 还是分值确实相同、
   仅用不同名字描述不同"角色种类"——若是后者，是否有必要在文档中说明
   "这些标签仅用于可读性，不影响打分"，以避免实现 grader 时产生歧义。
2. 检查 `role_oracle` 里使用的所有 `role` 字符串是否都能在 `score_values` 中找到
   精确匹配（大小写、连字符/斜杠等符号一致）。
3. 检查 `scoring_examples` 是否覆盖了 `score_values` 中**每一个数值**（不要求覆盖
   每个 key，但每个数值档位至少要有一条示例），且示例描述与 `oracle_notes.do_not_promote`
   不矛盾。
4. 检查 `empty_roles` 字段：如果非空，确认这些角色为何在当前 case 中未出现是否合理
   （例如某个难度档位特性未启用）。
5. **Anchor 条目唯一且可核对**（对应第 12.1–12.2 节，**BLOCKING**）：
   - `primary_anchor` 必须含 **`answer_function`**（bundle 标准答案名）、
     **`source_function`**（私有源侧映射）、`source_file`、`captured_span`、
     `anchor_definition`（或 `why`）、`score: 1`；
   - **不得**仅用 `primary_anchor.function` 承载源侧名而不提供 `answer_function`；
   - `role_oracle` 中 `role: "Anchor"` **有且仅有 1 条**，`answer_function` 与
     `primary_anchor.answer_function` 一致，`captured_span` 与 `primary_anchor` 完全一致；
   - 每条 `role_oracle[]` 宜含 `answer_function` + `source_function`（由 `gen_oracle_spans`
     自动写入为佳）；
   - `agent_hidden/build_meta.primary_anchor` 须镜像 `answer_function` + `source_function`；
   - 目录须符合第 12.5、14 节（`agent_visible/` + `agent_hidden/`）；
   - 若读完 case 仍无法回答"**agent 在 captures 里应提交的 anchor 函数名与坐标**"，判
     **BLOCKING**。
6. **Grader 评分语义是否自洽**（对应第 13 节）：`score_values`、`scoring_policy`、
   `scoring_examples` 是否足以让**未来 grader 实现**判定 agent 提交，而不仅靠人工脑补；
   须明确：**当前仓库通常无 `grade_submission.mjs`**，`verify.mjs` **不**评 agent 答案。

## 7. 可复现性 / 构建确定性检查

1. 在 `scripts/build.mjs` 中找到混淆器（如 javascript-obfuscator）的配置项，确认是否
   设置了固定 `seed`。如果开启了 `stringArrayShuffle`/`stringArrayRotate`/
   `controlFlowFlattening` 等随机性选项但**没有固定 seed**，则每次 `npm run build`
   产出的 `dist/` bundle 在结构上不可重现。
2. 确认 `oracle.hidden.json` 的 `captured_span`（行号/偏移/哈希）绑定的是
   `captures/devtools-source-dump/...`（一份**冻结快照**）还是 `dist/`（**每次构建
   重新生成**）。
3. 若绑定的是冻结快照：检查该 case 目录内**是否存在**"从当前 `src/` 重新生成
   `captures/` 并核对/更新 `oracle.hidden.json` 坐标"的脚本或文档化流程（通常为
   `scripts/gen_oracle_spans.mjs`，由 `build.mjs` 在拷贝 captures 后调用）。
   若不存在，明确指出："`src/` 与 `captures/`+`oracle.hidden.json` 之间没有自动化的
   一致性闭环，未来修改 `src/` 可能导致 oracle 坐标静默失效"（第 4 节检查的是
   "现在是否一致"，本节关注"未来是否会悄悄失效"）。
   若存在生成脚本：还必须通过第 11 节审查其**解析逻辑**是否正确——有脚本不等于
   坐标可靠。
4. 检查 `manifest.json` 里的 `captured_at` 时间戳与 `src/`、`oracle.hidden.json` 中其它
   时间/版本信息（如有）是否在合理的先后顺序上。
5. **依赖版本锁定（与第 1 点 `seed` 固定相互独立、需叠加判断）**：检查
   `package.json` 的 `devDependencies`（尤其 `javascript-obfuscator` / `rollup` /
   `vite` 等直接决定 bundle 字节级产物的工具）是否为**精确版本号**（非 `^`/`~`
   范围），以及是否存在并提交了**锁定文件**（`package-lock.json` /
   `pnpm-lock.yaml` / `yarn.lock`）。若为范围版本且无 lockfile，标注为
   **可复现性风险**：固定 `seed` 只保证"同一版本工具多次运行一致"，不能阻止
   "工具版本随时间/环境漂移"——不同机器 `npm install` 可能解析到不同
   `javascript-obfuscator`/`rollup`，其标识符命名规则、Rollup `$N` 去重后缀分配
   方式随之变化，导致 `captures/` bundle 字节级内容与 `gen_oracle_spans.mjs` 里
   依赖版本行为的 `ALIASES`/`BUNDLE_HINTS` 映射全部失效（修复见 `修改.md` M10）。

## 8. 泄漏边界检查（Leakage Boundary）

1. 在 `task.json` 全文（`question` + `public_constraints` + 其它字符串字段）中，逐一

## 10. 审查方法论陷阱与实战复盘（case001_browser_fingerprint）

本节记录真实审查中**曾发生过的错误、被忽视的问题及其延伸思考**。审查 agent 必须对照
自查，避免重复同类漏审。这些问题多数不会导致 `verify.mjs` 失败，但会导致 **grader
对 agent 答案打分系统性错误**——危害更大。

### 10.1 函数 span 解析：默认参数 `{}` 陷阱（BLOCKING 级）

**现象**：`primary_anchor`（`source_function: assembleBrowserFingerprint`）的 span 仅含
函数签名行（约 48 字节、1 行），不含函数体；`assembleDeviceProbe` 同理。

**根因**：从 `function name(` 后用 `indexOf("{", pos)` 找函数体时，先命中参数列表里的
默认参数 `s = {}`，而非真正的函数体 `{`。

**错误做法**：看到 `function assembleBrowserFingerprint(g, i, s = {}` 与 hash 匹配就认为
通过。

**正确做法**：
- 先匹配完整参数列表（括号计数），再在参数列表之后找第一个 `{`；
- 用括号平衡提取到函数结束 `}`；
- 验证切片长度、含 `return`/核心逻辑、以 `}` 结尾。

**延伸思考**：任何带默认参数、解构参数、TS 类型标注（若存在）的函数，都不能用"第一个
`{`"启发式；**生成器代码与审查代码都要走同一套严谨解析**。

### 10.2 混淆后同名函数：单候选短路（BLOCKING 级）

**现象**：bundle 中仅有一个 `function r(` 时，生成器对**所有**源侧 `r` 条目均返回同一
span（如 `1064031-1065138`），8 个语义不同的 `r` 全部碰撞。

**根因**：`if (named.length === 1) return named[0]` 类逻辑，或仅按函数名匹配、不做
源体区分。

**错误做法**：bundle 里能搜到 `function r` 就认为映射完成。

**正确做法**：
- 禁止"唯一同名即命中"短路；
- 为每个 `sourceKey` 建立评分/特征匹配（字面量、hex、结构、体积比、显式 `BUNDLE_HINTS`）；
- 维护 `usedStarts`，防止同一 bundle 函数被多个不同源函数抢占；
- 输出后做 4.1.4 去重审计。

### 10.3 过于宽泛的名称别名规则（BLOCKING 级）

**现象**：规则 `preferredName + '$1' === bundleName` 使**所有**源函数名为 `r` 的条目都
匹配到 `r$1`，导致 `g6.js::r` 抢占 `r$1`，`c2.js::r` 无法解析或错位。

**根因**：用单一启发式处理混淆重命名，未区分**不同源文件**的同名导出。

**正确做法**：
- 泛化规则（如 `$1` 后缀）必须与**显式 per-sourceKey 映射**（`BUNDLE_HINTS`）配合；
- 有显式 hint 时**只**接受 hint 列表内的 bundle 名；
- 无 hint 时才允许精确名匹配。

**延伸思考**：混淆器重命名是** per-scope **的，不能从"源侧都叫 r"推断"bundle 侧都叫
r$N"。审查时要列出**映射表**而非假设。

### 10.4 仅用字符串字面量做特征匹配（导致 unresolved / 误匹配）

**现象**：混淆后大量字符串迁入 string array，源里的 `'surface:delegate'`、`'ua'` 等
在 bundle 函数体中不可见，导致 score < 阈值 → unresolved；或不同函数因共享常量表而
同分歧义。

**根因**：`needlesFromSource` 只提取引号字符串，且过滤长度过短的关键 key（如 `'ua'`）。

**正确做法**：
- 同时提取：`0x` 十六进制、长整数、字符码数组、`Math.imul`/`>>>` 等结构特征；
- 数组/tuple key 用 `\['xx'\]` 模式保留短 key；
- 名称匹配优先于字面量分数；体积比作 tie-break；
- 对 obfuscated bundle **必读**目标函数附近原文再下结论。

### 10.5 歧义判定过严导致误报（或掩盖真问题）

**现象**：top 候选名称正确、分数 1.02，次优 1.0，因分差 < 0.08 判 ambiguous 失败。

**根因**：把"统计上接近"等同于"无法决策"，未把**名称匹配**作为硬优先。

**正确做法**：名称匹配（或 hint 匹配）且体积合理 → 直接接受；否则再看分差。

**审查延伸**：生成器 exit 1 时，要读 `failures` JSON 里每条是 `ambiguous` 还是
`unresolved`，分别对应不同修复方向。

### 10.6 Hash 自洽闭环：最隐蔽的"假通过"

**现象**：错误 span 被写入 `oracle.hidden.json`，再对**该文件中的 hash** 做校验，得到
44/44；`verify.mjs` 也可能通过（它不验证 span 语义）。

**根因**：把"切片 hash == oracle 记录"当成终点，未问"切片是不是对的那个函数"。

**审查铁律**：**轨 A + 轨 B 同时满足才算 PASS**（见 0.1 节）。报告中必须单独一节列出
`primary_anchor` 字节数、8 个 `r` 的 offset 是否唯一。

### 10.7 模板克隆未同步（元数据 / captures / verify 三角）

**现象**：`build_meta.hidden.json` 的 `trigger.steps` 仍为 `#emailInput` 等旧模板
selector，与 `task.json`/`verify.mjs` 的 `#probeAlias` 不一致；bundle 行数/字节数声明
过期。

**根因**：从其它 case 复制后只改 `src/`，未同步基础设施与 `captures/`。

**正确做法**：第 1 节矩阵**每一格**都要填具体值；发现 selector 集合不一致时，立即
做 4.2 检查 captures 是否也为旧快照。

### 10.8 基础设施填充与死代码（结构性缺陷）

**现象**：`README.md` 数百行 `readme-row`；`package.json` 的 `local_notes`；
`scripts/*.mjs` 末尾大量未引用常量以满足行数门槛。

**忽视后果**：agent 浪费 token、掩盖真实构建逻辑、使"行数要求"失去度量意义。

**正确做法**：第 3.2 节逐文件清查；建议行数门槛**仅针对 `src/`**。

### 10.9 其它曾忽视项（检查清单）

- `task.json:question` 为中文 → 第 2 节硬性违规；
- 缺少固定 obfuscator `seed` → 第 7 节，每次 build 坐标漂移；
- 缺少 `gen_oracle_spans.mjs` → 改 src 后 oracle 只能手改，极易错；
- `keyRing` 在 `l0.js` 与 `n0.js` 源体相同但 bundle 为 `keyRing` vs `keyRing$1` →
  需显式 hint，不能假设共享 span；
- 对 1.7MB bundle 做全量 AST 解析导致审查/生成脚本挂起 → 应用括号扫描 + 字符串掩码；
- 后台 `build.mjs` 长时间无输出 → 审查时应确认是否 stuck，不能假设 build 已完成。

### 10.14 把 build_meta / oracle 混进 Agent 上下文（审查表述误区）

**现象**：审查报告、流程图或模拟评分里写"agent 读取 `build_meta.primary_metric`"、
"agent 应输出 `answer_function`"、或把 `score_values` 档位当作 agent 推理输入。

**事实**：参赛 Agent **只能**读 `task.json` + `captures/`。`build_meta.hidden.json`、
`oracle.hidden.json`、`src/`、`scripts/` 对 agent **不可见**。Agent 不知道 0.7 分、
`Nested target-specific helper`、`primary_anchor` 等私有概念。

**正确三分轨**：
- **Agent 轨**：`task.json` → 在 captures 推理 → 提交 `{ function_name, file, slice }`；
- **Grader 轨**（私有）：读 agent 提交 + `oracle.hidden.json` → 映射 span → 取 score；
- **维护者轨**（私有）：`build_meta`、`gen_oracle_spans`、`verify.mjs`、审查文档。

**正确做法**：题面用 `function_name`/`slice`；oracle 用 `answer_function`/`captured_span`；
审查时显式写出两轨字段映射，但**不得**假装 agent 能看到 oracle 字段名。

### 10.16 未做物理目录分区（扁平布局遗留）

**现象**：`<case_id>/task.json`、`oracle.hidden.json`、`src/` 仍同在 case 根目录；
审查报告把 `build_meta` 与 `task.json` 并列当作"agent 可读文件清单"。

**事实**：标杆 `case001_browser_fingerprint` 已拆为 `agent_visible/`（仅 task+captures）
与 `agent_hidden/`（oracle、build_meta、src、scripts、dist）。评测 harness 应只打包
`agent_visible/`。

**正确做法**：第 12.5、14 节——审查判 BLOCKING；修改时按 14.3 迁移，不以旧布局为默认。

### 10.15 Grader 输出 JSON 无统一 schema（勿臆造字段）

**现象**：模拟评分输出 `{ score, role, match_basis, reason }`，误以为仓库有统一 grader
输出规范；尤其 `match_basis` 等字段在 case 中**不存在**。

**事实**：评分**语义**由 `oracle.hidden.json` 声明（`score_values`、`role_oracle`、
`scoring_policy`、`scoring_examples[].matched_reason`）；**可执行 grader 与输出 JSON
schema 当前通常未实现**。`verify.mjs` 只验 case 结构/运行时，不评 agent 提交。

**正确做法**：实现 grader 时自行定义输出 schema；分值/角色必须来自命中的
`role_oracle[].{score,role,answer_function}`，理由可参照 `scoring_examples` 模板。

### 10.11 把源侧函数名误当作标准答案（审查与 oracle 设计误区）

**现象**：oracle 仅写 `primary_anchor.function: assembleBrowserFingerprint`，维护者/grader
默认 agent 也应答该名；或用 `grep` 源侧名判定 captures 是否有效。

**事实**：Agent **只能**看 `captures/`。`assembleBrowserFingerprint` 是 `src/` 里的
`source_function`；混淆后 bundle 里可能是 `r$1`、`m$6` 或碰巧保留原名——**标准答案
必须是 `answer_function`（bundle 切片行首名）+ `captured_span`**，不是 source_function。

**正确 schema**（`case001_browser_fingerprint` 已采用）：
```json
"primary_anchor": {
  "answer_function": "assembleBrowserFingerprint",
  "source_function": "assembleBrowserFingerprint",
  "captured_span": { "...": "..." },
  "answer_basis": "Agent-visible corpus only; grade by span + answer_function."
}
"role_oracle": [{
  "function": "r action router",
  "source_function": "r",
  "answer_function": "r$1",
  "captured_span": { "...": "..." }
}]
```

**正确做法**：
- Grader **主判据**：`captured_span` hash/offset；**辅判据**：`answer_function`；
- `source_function` 仅供 `gen_oracle_spans` 维护，**不得**作为 agent 默认应答空间；
- `acceptable_hit_conditions` / `scoring_policy` 须写明上述优先级；
- 报告 A4 **先写 `answer_function`**，再写 `source_function`（私有）。

### 10.12 题面承诺 console 输出但人手测不到（BLOCKING 级）

**现象**：`task.json` 写"submit 后控制台出现 `browser_fingerprint`"，README 也这么写，
但按步骤操作浏览器**没有任何相关 log**；或只有 decoy 的 `device_hash` log。

**根因**：submit gate 未打开、sink 未执行、verify 监听了过宽/过窄的模式、interaction
与 verify 不一致、build 产物与 captures 不一致等。

**审查要求**：见第 5.1 节——**必须实测**，不能只看 verify 源码"看起来会测"。

### 10.13 读完 case 仍不知道 anchor 是哪个函数（BLOCKING 级）

**现象**：`oracle.hidden.json` 很大，但没有清晰的 `primary_anchor`；或 anchor 仅散落在
自然语言 `anchor_definition` 里；或多个函数都像 anchor；维护者自己也不确定。

**根因**：case 从模板改造时未写入 `primary_anchor`；`role_oracle` 未标 `Anchor`；
`build_meta` 与 oracle 脱节。

**正确做法**：第 12.1 节硬性字段 + 报告 A4 身份卡——**每个 case 一条且仅一条 anchor**。

### 10.10 延伸思考：什么样的 case 最容易漏审

1. **多同名不同源函数**（`r` 链、wrapper 链）；
2. **锚点函数带默认参数**；
3. **混淆强度高 + string array**；
4. **oracle 条目多（40+）**；
5. **captures 为手工拷贝而非 build 管线产出**；
6. **verify 只测运行时行为，不测 oracle 坐标**。

对此类 case，审查时间应显著加长；**禁止抽样**。

## 11. `gen_oracle_spans.mjs` 专项审查（若存在则必做）

许多 case 的 oracle 坐标依赖该脚本从**当前** `captures/` bundle 反推。脚本 bug =
oracle 全错但可能 hash 自洽。审查时必须**读代码 + 跑脚本 + 独立审计输出**。

### 11.1 实现必查项

| 检查项 | 合格标准 | 常见失败 |
|---|---|---|
| 参数列表跳过 | 提取函数体前先闭合 `(...)` | 命中 `s = {}` 截断签名 |
| 函数体括号平衡 | 字符串/模板串内括号不计入深度 | 半截函数、hash 仍"可算" |
| 禁止唯一同名短路 | 不得 `named.length===1` 直接返回 | 8 个 `r` 合并 |
| 显式混淆名映射 | 多源同名有 per-`sourceKey` hint | 泛化 `$1` 规则误匹配 |
| 写入 answer_function | 每条 role_oracle + primary_anchor 写入 bundle 切片行首名 | 仅写 source 名，agent 无法对标 |
| 占用去重 | 同一 bundle 起点不得被不同源体抢占 | g6 抢 r$1 |
| 歧义处理 | 名称/hint 匹配优先于分差阈值 | 正确候选被判 ambiguous |
| 特征集 | 含 hex/结构/体积，不只字符串 | 大量 unresolved |
| 生成后校验 | 完整性 + 跨 sourceKey 重复 span | 仅报 hash_verified |
| 性能 | 1MB+ bundle 不应依赖全量 AST 卡死 | 审查/build 挂起 |

### 11.2 运行后必做输出核对

执行 `node scripts/gen_oracle_spans.mjs` 后，记录并审查：

```json
{
  "role_oracle_updated": "<应等于 role_oracle 条目数>",
  "hash_verified": "<应等于条目数>",
  "anchor_bytes": "<primary_anchor 应 >100>",
  "anchor_answer_function": "<bundle 切片行首名，agent 标准答案标识>",
  "anchor_source_function": "<src/ 私有映射名，可与 answer_function 不同>",
  "duplicate_span_groups": "<应为 0，或仅有源体 identical 的合理解释>"
}
```

并**独立**验证（不得只看脚本 stdout）：
- `primary_anchor` 切片含完整函数体；
- `primary_anchor.answer_function` 等于该切片内 `function <名>(` 行首名；
- 所有 `role_oracle[].answer_function` 已从 bundle 切片提取，多 `r` 的 `answer_function`
  与 offset 均唯一；
- `bind delegated click` 等关键条目切片内含可辨识逻辑（如 `surface:delegate`）；
- 44/44 hash 是对 **captures bundle 原文** 重算，而非对 oracle 字符串复读。

### 11.3 与 `build.mjs` 的衔接

- `build.mjs` 应在复制 `dist/` → `captures/` 后调用 `gen_oracle_spans.mjs`；
- 固定 `seed`（若使用 obfuscator）；
- 审查时建议完整跑 `npm run build`（或等价命令）再跑生成器，确认管线闭环。

## 12. 五项硬性结构要求（跨 case 通用，审查必做）

以下五项来自 benchmark 维护实战中的**高频结构性缺陷**，与混淆、评测可解释性、
agent 可见边界、目录分区、task 可完成性直接相关。任一不满足，通常应判 **BLOCKING**。

### 12.1 每个 case 的 Anchor 必须唯一、明确、可核对

**问题背景**：当前仓库中部分 case 读完所有文件后，维护者仍无法确定"anchor 到底是哪个
函数"——这会使 grader 无法落地，agent 答案无法客观评分，case 失去 benchmark 意义。

**硬性要求**（全部满足才算 PASS）：

| 字段/检查 | 位置 | 要求 |
|---|---|---|
| `primary_anchor.answer_function` | `oracle.hidden.json` | 非空，**bundle 切片行首名**（= agent 按 task.json 提交的 `function_name`） |
| `primary_anchor.source_function` | 同上 | 非空，**`src/` 私有映射名**（维护者/gen 用，非 agent 应答空间） |
| `primary_anchor.source_file` | 同上 | 非空，指向 `src/` 内真实文件 |
| `primary_anchor.captured_span` | 同上 | 完整坐标 + hash；**grader 主判据** |
| `primary_anchor.answer_basis` | 同上 | 明文写明"以 captures span + answer_function 为准" |
| `primary_anchor.why` / `anchor_definition` | oracle / build_meta | 说明**为何是该函数**而非邻近 helper |
| `role: "Anchor"` 条目 | `role_oracle[]` | **有且仅有 1 条**；`answer_function` + span 与 `primary_anchor` 一致 |
| `role_oracle[].answer_function` | 同上 | 每条宜有；从 bundle 切片提取，供 grader 对照 agent 返回值 |
| `build_meta.primary_anchor` | `build_meta.hidden.json` | 镜像 `answer_function` + `source_function` + span |
| `acceptable_hit_conditions` | oracle | 写明 agent 以 span + `answer_function` 匹配，非 `source_function` |
| 评分示例 | `scoring_examples` | score=1 示例引用 **captured span / answer_function**，非源侧名 |

**禁止**：
- 只有自然语言描述、没有 `primary_anchor` 对象；
- 使用遗留字段 `primary_anchor.function` / `bundle_function` 承载标准答案；
- 仅有 `source_function` 或 `function`（源侧名）而无 `answer_function`；
- 多个条目都标 `Anchor` 或都像 anchor 却无排他说明；
- `answer_function` 与 bundle 切片行首名不一致；
- 维护者/ grader 需"猜" anchor 在 bundle 里叫什么。

**审查输出**：报告 **A4 Anchor 身份卡**（见第 9 节）为**必填**——读报告者 10 秒内
应能答出：**`answer_function`（标准答案名）**、bundle 偏移/字节数、`source_function`
（私有）、为何唯一。

### 12.2 标准答案在 captures（`answer_function`）≠ 私有源侧映射（`source_function`）

**问题背景**：Agent **只能**访问 `captures/devtools-source-dump/**/*.js`，看不到 `src/`。
因此它**不可能知道** `assembleBrowserFingerprint` 这类仅存在于源侧的命名——除非混淆后
bundle 碰巧仍保留该字面量（不可靠）。若 oracle 把源侧名当作"标准答案"，benchmark 在
逻辑上不成立。

**三分轨模型**（审查、出题、实现 grader 时必须分清）：

```
【Agent 轨 — 仅 task.json + captures/】
  输入：question, public_constraints, answer_format.response_schema
  输出：{ function_name, file, slice: { start_line, end_line, start_offset, end_offset, code } }

【Grader 轨 — 私有 oracle.hidden.json】
  输入：agent 提交 JSON
  映射：function_name → answer_function；slice → captured_span
  输出：score（来自 role_oracle[].score）、role（来自 role_oracle[].role）

【维护者轨 — build_meta / src / scripts，agent 不可见】
  source_function, source_file, gen_oracle_spans, verify.mjs, build_meta.difficulty ...
```

**Agent 提交 ↔ Oracle 金标准字段映射**（grader 实现时遵循）：

| Agent 提交（task.json 规定） | Oracle 私有（grader 用） |
|---|---|
| `function_name` | `role_oracle[].answer_function` / `primary_anchor.answer_function` |
| `file` | `captured_span.file` |
| `slice.start_offset` / `slice.end_offset` | `captured_span.start_offset` / `end_offset` |
| `slice.code` | bundle 切片原文（用于 hash/完整性校验） |
| `slice.start_line` / `slice.end_line` | `captured_span.start_line` / `end_line`（辅） |

**Grader 优先级**：
1. **主判据**：`slice` 与某条 `captured_span` 唯一匹配（hash/offset/完整函数体）；
2. **辅判据**：`function_name` 与命中行的 `answer_function` 一致；
3. **`source_function` 不参与**默认 agent 评分。

**审查动作**：
1. 在 `captures/` bundle 按 `captured_span` 切片，读取 `answer_function`（`function` 行首）；
2. 核对 oracle 中 `primary_anchor.answer_function` 与该名**一致**；
3. 在 `src/` 核对 `source_function` 存在——仅验证 gen 映射链，**不**要求 agent 知晓；
4. 对多同名源函数（如 8 个 `r`），检查各条目 `source_function` 相同但 `answer_function`
   不同（例：`source_function: r` → `answer_function: r$1` / `r$3` / `r$d`）；
5. `verify.mjs` / `bundle_contains_answer_code` **不得**依赖源侧函数名字面量（应用
   `answer_function` 或混淆后仍残留的结构特征，如 `isSurfacePart`、`encodeFingerprintDigest`）；
6. `acceptable_hit_conditions` 与 `scoring_policy.source_level_answer` 须与上述一致。

**延伸**：`gen_oracle_spans.mjs` 职责是从 `source_function` 定位 bundle 切片，并**写回**
`answer_function`；不是让 agent 反查 `src/`。

**推荐 schema**（`case001_browser_fingerprint` 已采用；新 case 应遵循）：
```json
"primary_anchor": {
  "answer_function": "assembleBrowserFingerprint",
  "source_function": "assembleBrowserFingerprint",
  "source_file": "src/z0/k7/q3/t9.js",
  "captured_span": { "...": "..." },
  "answer_basis": "Agent-visible corpus only; grade by span + answer_function."
}
```
- `answer_function`：从 `captured_span` 切片内 `function <名>(` 自动提取；
- `source_function`：维护者/gen 映射到 `src/` 的私有名，**非** agent 默认应答空间；
- 生成后应 `delete` 遗留的 `function` / `bundle_function` 字段，避免 grader 误读。

### 12.3 按 Task 交互后必须能 Console 观测到题面所述结果

**问题背景**：题面通常要求"按某序列操作后，在 console 中看到某 action 的某 field 值"。
实测存在 **verify 绿但人手看不到 log** 的 case——属于致命结构缺陷。

**硬性要求**：

1. **题面一致**：`task.json: interaction[]` 的每一步都能在 `verify.mjs` 中找到等价操作
   （顺序、selector、value 一致）；
2. **sink 真实存在**：在 `src/` 的 submit/sink 路径上存在对该 field 的 `console.log`
   （或 verify 认可的等价 observable）；
3. **端到端可观测**：
   - 跑 `node scripts/verify.mjs` 必须触发并捕获该 log；
   - 审查报告中记录**样例 log 行**（可脱敏）或明确写"实测未出现"并 BLOCKING；
4. **gate 可打开**：若路径依赖 `gate`、`armed` 计数等，确认题面交互能使其为 true——
   不是"理论上有代码但题面步骤永远走不到"：
5. **与第 5.1 节联动**：verify 的 `console_browser_fingerprint_exists`（或同类检查）
   必须通过，且审查 agent 相信该检查**不是假阳性**（读过 `targetPromise` 实现）。

**人工 smoke test 步骤**（审查 agent 必做或等价验证）：
```text
npm run build（若怀疑产物过期）→ node scripts/serve.mjs（或 verify 内置 server）
→ 按 task.json interaction 逐步操作 → 打开 DevTools Console → 确认题面 field 出现
```
若环境不允许开浏览器，必须精读 `verify.mjs` 的 Playwright 流程并在报告中说明
"console 监听逻辑已核对，等价于实测"。

### 12.4 Agent 可见边界与提交格式（task.json 硬性要求）

**问题背景**：若题面未规定 agent 输出 JSON 结构，grader 无法稳定解析"函数名+切片"；
若审查/agent 说明把 `build_meta`/`oracle` 当作 agent 输入，则整个 benchmark 前提不成立。

**Agent 唯一能读的目录**（默认：`agent_visible/`，除非评测 harness 另行声明）：

| `agent_visible/`（可见） | `agent_hidden/` 及 case 外（不可见） |
|---|---|
| `task.json` | `oracle.hidden.json` |
| `captures/`（`visible_corpus` 范围内，通常 `**/*.js`） | `build_meta.hidden.json` |
| | `src/`、`scripts/`、`dist/`、`package.json`、一切 `*.hidden.json` |

**`task.json: answer_format` 最低要求**（`case001_browser_fingerprint` 已采用）：

```json
{
  "response_type": "json",
  "response_schema": {
    "function_name": "bundle 切片行首 function 名（非源侧名）",
    "file": "captures/ 下 .js 路径",
    "slice": {
      "start_line": "整数",
      "end_line": "整数",
      "start_offset": "0-based 字节偏移",
      "end_offset": "0-based 字节偏移（exclusive）",
      "code": "完整函数源码文本"
    }
  },
  "example": { "...": "占位示例，不得泄漏真实 anchor 名/坐标" }
}
```

**审查检查**：
1. `question`/`public_constraints` 是否要求"单个 JSON 对象"且指向 `answer_format`；
2. `function_name` 描述是否强调"as it appears in captures"；
3. `slice.code` 是否要求完整函数（禁止签名残片——见第 10.1 节）；
4. `example` 是否用占位名/假坐标，**未泄漏** `primary_anchor` 真实答案；
5. agent 合规提交能否唯一映射到 `primary_anchor`（score=1）或某条 `role_oracle`；
6. **不得**在 `task.json` 要求 agent 填写 `answer_function`、`source_function`、
   `captured_span`、`score` 等 oracle 字段。

**与第 8 节泄漏检查联动**：`task.json` 不得出现 oracle 独有的真实 anchor 函数名/坐标；
`example` 允许出现 captures 下的**文件路径**（agent 本就会看到），但函数名/行号须占位。

### 12.5 物理目录分区：`agent_visible/` 与 `agent_hidden/`（硬性）

**问题背景**：仅靠文档声明"agent 不能看 oracle"不够——若 `task.json`、`oracle.hidden.json`、
`src/` 仍平铺在 `<case_id>/` 根下，评测打包极易误发私有文件，且审查 agent 易混淆可见边界。
`case001_browser_fingerprint` 已采用**物理隔离**。

**canonical 目录树**（审查与修改的**唯一标杆**，见第 14 节）：

```text
<case_id>/
├── README.md                 # 分区说明（给维护者；agent 不读）
├── agent_visible/            # ← 评测 harness 只打包此目录
│   ├── README.md
│   ├── task.json
│   └── captures/
│       └── devtools-source-dump/...
└── agent_hidden/             # ← 维护者 / grader / CI
    ├── README.md
    ├── package.json
    ├── oracle.hidden.json
    ├── build_meta.hidden.json
    ├── src/
    ├── scripts/              # build.mjs, verify.mjs, serve.mjs, gen_oracle_spans.mjs
    └── dist/                 # 构建产物；build 后同步进 agent_visible/captures/
```

**硬性要求**（全部满足才算 PASS）：

| 检查 | 要求 |
|---|---|
| `agent_visible/` 存在 | 仅含 agent 题面与语料（`task.json` + `captures/`）；**不得**含 oracle、src、scripts |
| `agent_hidden/` 存在 | 含 `oracle.hidden.json`、`build_meta.hidden.json`、`src/`、`scripts/`、`package.json` |
| 根目录无散落关键文件 | 根下**不得**再出现独立的 `task.json`/`oracle.hidden.json`/`src/`（旧布局 = BLOCKING） |
| 脚本路径 | `build.mjs` 写入 `agent_visible/captures/`；读写 oracle 用 `agent_hidden/` 为根 |
| oracle 路径引用 | `captured_span.file` 用 **agent 相对路径**（`captures/...`，相对 `agent_visible/`）；`target_reference.task_file` 用 `agent_visible/task.json` |
| 构建入口 | `cd agent_hidden && npm run build`（或等价） |

**审查与修改纪律**：
- **审查**：未分区或分区错误的 case → **BLOCKING**，报告中单列 A7；
- **修改**：不得仅在旧扁平结构上改内容——须**迁移**为上述树，并以
  `case001_browser_fingerprint` 的文件相对位置为准同步改脚本路径。

## 13. Grader 评分框架（声明式规范，与 verify 分工）

本节说明**如何给 agent 提交打分**——语义由 oracle 声明，**不是** agent 可见信息。
当前 `benchmark_cases/<case_id>/` 内**通常没有**可执行 grader（无 `grade_submission.mjs`）；
`scripts/verify.mjs` 验证 case 结构与运行时，**不读取、不评判** agent 提交的 JSON。

### 13.1 评分语义写在哪里

| 字段/文件 | 作用 |
|---|---|
| `oracle.hidden.json: score_values` | `role` 字符串 → 分值（如 `Nested target-specific helper` → 0.7） |
| `oracle.hidden.json: role_oracle[]` | 每条候选函数的 `captured_span`、`score`、`role`、`answer_function` |
| `oracle.hidden.json: primary_anchor` | anchor 金标准（score=1） |
| `oracle.hidden.json: scoring_policy` | 算法规则（top_1、span 重叠、歧义、源路径答案无效等） |
| `oracle.hidden.json: scoring_examples` | 各分值档位的 `matched_reason` **模板**（非强制输出 schema） |
| `oracle.hidden.json: acceptable_hit_conditions` | 命中/排他条件 |
| `build_meta.hidden.json: task_contract.primary_metric` | 维护者声明指标名（agent **不可见**） |

### 13.2 Grader 算法（审查时须能复述）

```text
1. 解析 agent 提交（格式以 task.json: answer_format.response_schema 为准）
2. 在 captures bundle 按 slice.offset 重切片，校验完整函数体 + hash（可选）
3. 按 scoring_policy.span_overlap_policy 在 role_oracle 中找唯一命中行
4. 取命中行的 score、role、answer_function
5. 辅判：submission.function_name === 命中行.answer_function
6. 若无唯一命中 → score = 0（见 scoring_examples 中 score=0 的 matched_reason）
```

**示例**（agent 提交 `encodeFingerprintDigest` 的 slice，私有 grader 判定）：
- 命中 `role_oracle` 中 `answer_function: encodeFingerprintDigest` 行；
- `score: 0.7`，`role: Nested target-specific helper`（来自该行，不是 agent 知道的）；
- 理由可参照 `scoring_examples` 中 score=0.7 的 `matched_reason` 模板。

### 13.3 什么没有统一规范（勿臆造）

- **Grader 输出 JSON 的字段名**（如 `match_basis`、`reason`）——仓库未定义；实现 grader 时自定；
- **Agent 提交字段名**——以 `task.json` 为准（`function_name`、`slice`），**不是** `answer_function`；
- **可执行 grader 脚本**——审查时检查"语义是否足以实现"，不要求仓库内已存在。

### 13.4 verify.mjs 与 grader 的边界

| 工具 | 读什么 | 不做什么 |
|---|---|---|
| `verify.mjs` | `agent_hidden/` 下 `task.json` 逻辑、`agent_visible/captures/`、`src/` | 不评 agent 提交的函数名/切片 |
| `gen_oracle_spans.mjs` | `agent_visible/captures/` + `agent_hidden/src/` 映射 | 不评 agent 答案 |
| grader（待实现） | `agent_visible` 提交 + `agent_hidden/oracle.hidden.json` | 不替代 verify 的结构/运行时检查 |

## 15. 难度声明的构造效度：声明的难度轴是否真的是解题瓶颈

本节与第 9 节报告 F 表互补：F 表问"`build_meta` 声明的混淆/异步/调用深度等特性是否
**真实存在**于代码中"；本节问"即使这些特性真实存在，它们是否真的是 agent 解出本题
的**主要瓶颈**，还是存在一条绕过它们的捷径"。这是**构造效度（construct validity）**
问题——通常**不构成 BLOCKING**，但会让"难度"声明名不副实。

1. **关键标识符是否在混淆后仍语义自描述**：列出 `oracle.hidden.json: role_oracle`
   中 `score >= 0.5`（Anchor / Nested target-specific helper / Core utility）的所有
   `answer_function`，逐一在 `captures/` bundle 中确认其名称是否仍是有意义的英文
   标识符（而非 `a`/`b`/`r$3` 这类被 mangle 的名）。同时列出与之"字面/语义相似"的
   `Off-chain`/decoy 条目的 `answer_function`。
2. **捷径可行性估算**：若步骤 1 的"语义自描述"标识符（含目标与诱饵）总数较小
   （个位数到十几个），评估"对 bundle 做一次大小写不敏感关键词搜索（搜题面
   `question`/`observable.field` 的核心名词）即可把候选收窄到这个小集合"是否可行。
3. **对照 build.mjs 混淆配置**：检查 `obfuscationOptions` 的
   `identifierNamesGenerator`/`renameGlobals`/`compact` 等——是否存在
   `renameGlobals:false`（或等价）使模块顶层函数名不被混淆、只 mangle 局部变量的
   **非对称**混淆，且恰好保留了步骤 1 中"答案承载"标识符的可读性？
4. **结论**：若 1–3 显示"关键词搜索即可收窄到覆盖所有 score≥0.5 条目的小集合"，
   则记为**构造效度风险**（非 BLOCKING）："`build_meta` 关于调用深度/异步边界/
   控制流展平的难度描述，可能不是 agent 实际解题的主要瓶颈；真实瓶颈是小候选集内
   的语义消歧。" 这是一个需要做设计决策的修改项（如实改措辞 vs 提高混淆对称性），
   两条候选路径见 `修改.md` M11。

**与第 12.2 节的协调（重要，避免误判）**：`answer_function`（标准答案名）"在 bundle
中可读"本身是 grader 与 agent 所**必需**的——agent 要能在 captures 里提交该名。因此
本节的风险**不是**"标识符不该可读"，而是"**可读到足以让一次关键词搜索就绕过所声明
的难度**"。判定时务必区分这两者，不要因为 `answer_function` 可读就误判为缺陷。
